# minimp3 单文件播放链路优化策略

## 1. 文档目的

这份文档只讨论一件事：在当前工程里，如果不做文件拆分，只保留一个播放类、一个实现文件，应该怎样把现在的 minimp3 改成更干净、更稳定、更容易维护的版本。

这里说的“一个文件”是指：

- 播放控制
- HTTP 拉流
- MP3 解码驱动
- PCM 输出节奏控制

都可以先放在同一个实现文件里完成。

这份文档不要求你立刻重构目录，也不要求你马上改成多模块架构。目标是先把当前播放闭环收敛到最小可控版本。

---

## 2. 先看当前工程里的真实边界

在当前仓库里，这条播放链已经有几个很明确的边界，不需要重新发明：

1. 控制面入口已经存在。
   - DLNA 控制面已经重写到 includes/wlan/dlna 下，当前边界中心是 playback_bridge 和 renderer。
   - 这说明播放器不需要自己处理 DLNA 协议，它只要接受控制面下发的 set_uri、play、pause、stop 这几类动作。

2. HTTP 工具已经存在。
   - http_utils 已经提供 URL 解析、DNS 解析、HTTP 头提取、字符串清洗等基础能力。
   - 播放类不需要再额外引入新的 URL/HTTP 抽象层。

3. IIS 输出队列已经存在。
   - iis.cpp 里已经有 DMA 环形缓冲、pending_frames、水位补偿、预缓冲启动等机制。
   - 这意味着播放器不应该再自建第二套 PCM 队列，否则会出现双重缓冲、双重节流、调试困难。

4. 后台播放任务已经存在。
   - main.cpp 已经单独启动了 minimp3_task。
   - 这说明播放器天然适合做成“一个长期运行的服务循环”，而不是一次调用就完成所有事情的同步函数。

基于这几个事实，最合理的方向不是继续往 minimp3 里堆更多探测和容错逻辑，而是把它收缩成一个真正的播放服务类。

---

## 3. 当前 minimp3 的根问题

现在这份 minimp3 最大的问题不是“功能少”，而是“职责太杂”。

它同时承担了：

- URL 状态管理
- 播放开关管理
- socket 建连
- HTTP 请求拼接
- HTTP 头解析
- ICY 元数据过滤
- 非 MP3 流识别
- ID3 跳过
- MP3 重同步
- 解码驱动
- 采样率切换防抖
- PCM 推送
- 与下游队列的背压配合
- 弱网重连
- 各种诊断日志

这些逻辑不是都错，但全部揉在一个热循环里，会造成三个直接后果：

### 3.1 类的身份失真

这个类名叫 minimp3，但它实际上不是“解码器封装”，而是“网络播放器服务”。

如果一个类名表示的是第三方库，类行为却覆盖了控制面、网络、缓冲和输出，那么后续任何人接手都会误判边界。

### 3.2 热路径被诊断分支淹没

播放主循环最该做的只有四件事：

1. 收数据
2. 解码
3. 推 PCM
4. 根据 stop/url 变化收口当前会话

但现在主循环里塞了太多“如果这个流像 AAC”“如果像 HTML”“如果像 JSON”“如果 frame_bytes 恰好等于整个窗口”“如果候选 sync 偏移过大”之类的旁路逻辑。逻辑一多，问题就不是“复杂但强大”，而是“你很难证明它现在到底会怎么走”。

### 3.3 节奏控制被拆成两半

当前工程真正决定“什么时候该暂停喂 IIS、什么时候该继续”的逻辑，其实有一半还在应用装配层里的 push_pcm_with_closed_loop，一半在 minimp3::stream_mp3_to_iis 里。

这会产生一个很差的结构：

- 播放类不知道自己真正的输出节奏
- WiFi 任务却知道 PCM 输出水位

这两个职责放反了。

## 4. 单文件方案的总目标

如果只允许保留一个文件，我建议把目标收敛成下面这句话：

**让 minimp3 变成一个单线程、单会话、单下游队列的播放服务。**

这句话展开以后，有四个关键约束：

1. 单线程
   - 只有一个后台任务真正执行拉流和解码。
   - 控制面回调不做网络操作，只改“期望状态”。

2. 单会话
   - 同一时刻只服务一个 URL。
   - URL 变化时，旧连接和旧解码状态立即失效，不做多路并发。

3. 单下游队列
   - 下游只认 IIS 的 DMA 队列。
   - 播放类不再额外维护“PCM 二级缓存队列”。

4. 单责任主循环
   - 主循环只围绕“准备会话、建连、收流、解码、推送、清理、重试”这条主线。
   - 除必要的兼容逻辑外，不再在热路径上堆调试型分支。

---

## 5. 这个类应该变成什么

如果你暂时不改文件名，也不改外部调用名，那么 class minimp3 最适合演化成下面这个角色：

**它不是 miniMP3 解码器包装类，而是接收 URL 控制、驱动 HTTP 拉流、调用 miniMP3 解码并把 PCM 按节奏送进 IIS 的播放服务类。**

因此这个类的对外接口应该尽量薄，对内状态应该尽量完整。

### 5.1 对外只保留最小控制接口

建议最终只保留下面几类入口：

- prepare_url(url)
- play_url(url)
- stop_playback()
- clear_playback_url()
- run_stream_service() 或 stream_mp3_to_iis()

其中：

- prepare_url 只更新待播 URL，不建连
- play_url 负责把“有 URL 且请求播放”这两个条件置为真
- stop_playback 只请求停止，不做复杂清理
- clear_playback_url 负责把 URL 和播放请求一起清空
- run_stream_service 作为后台任务入口，永久循环执行

也就是说，控制面只能“发意图”，不能“直接干活”。

如果结合你现在已经重写好的 wlan/dlna 结构来看，播放器更准确的上游边界应该是：

- renderer 负责接住控制点请求
- control_router 负责解析 SOAP 动作
- playback_bridge 负责把动作转成播放器可执行命令
- minimp3 只负责执行这些命令对应的数据面行为

这样单文件播放器虽然没有拆模块，但它在系统中的位置仍然是清楚的。

### 5.2 对内统一收口所有播放状态

当前散在静态变量和外层回调里的状态，应该被播放器自己完整持有。至少要有：

- requested_url
- active_url
- play_requested
- stop_requested 或 generation
- current_hz
- socket_fd
- http_connected
- buf_start
- bytes_in_buf
- decoder_initialized

如果还要做得更稳一点，再加两个：

- session_generation
- active_generation

这样当 URL 被更新、或者用户点了 Stop 时，主循环只要发现 generation 不匹配，就能立刻丢弃当前流上下文并开始新一轮会话，不需要靠多组布尔变量互相拼。

## 6. 推荐的单文件内部结构

虽然只写一个文件，但内部还是应该分区。不要再把所有辅助函数都散在匿名命名空间里没有层次地堆着。

建议在一个 cpp 文件里按下面顺序组织：

```cpp
class minimp3 {
public:
    // 控制入口

private:
    struct SessionState;
    struct OutputHooks;

    // 1) 控制状态
    // 2) 输出绑定
    // 3) 主循环
    // 4) 会话准备/清理
    // 5) HTTP 建连与收包
    // 6) 解码推进
    // 7) PCM 推送节奏控制
    // 8) 少量必要工具函数
};
```

这不是为了“好看”，而是为了避免以后再次回到“网络工具函数和会话状态更新函数混在一起”的局面。

### 6.1 SessionState 应该是什么

建议把每次播放连接相关的临时状态都塞进一个内部会话结构，而不是继续靠十几个局部变量横飞：

- 当前 socket
- 当前解析后的 host/path/port
- HTTP 头是否读完
- 当前接收窗口
- 当前解码器对象
- 当前采样率
- 当前是否已锁定首帧
- 当前是否需要重连

这样做的好处是：

- stop 时只清理 SessionState
- URL 变化时只废弃 SessionState
- 会话外的控制状态不需要跟会话内的 socket 状态互相缠绕

## 7. 最小可运行闭环应该怎么走

这是当前项目最重要的部分。

你真正需要的不是“大而全的播放器状态机”，而是一条稳定的最小闭环：

1. playback_bridge 或同等装配层把 URL 和 play_requested 写进去
2. 后台任务看到“现在应该播放”
3. 建立 HTTP 连接
4. 读取响应头并定位到 body
5. 把 body 字节流持续送入解码窗口
6. 解出 PCM 后按 IIS 水位推送
7. 停止、URL 变化、EOF、网络错误时收口本次会话
8. 如果仍然要求播放同一个 URL，则按退避策略重连

这就是完整闭环，不需要再引入第二层架构解释。

### 7.1 主循环推荐写法

建议后台任务永久循环只做下面的状态分支：

#### 分支 A：当前没有播放请求

- 如果 play_requested 为假，休眠短时间
- 不建连
- 不清空 requested_url
- 不做任何探测

#### 分支 B：当前有播放请求，但还没有活动会话

- 复制 requested_url 到 active_url
- 初始化 SessionState
- 建立 socket
- 发送 GET
- 读取 HTTP 头
- 把首包 body 放入接收窗口

#### 分支 C：当前活动会话正在播放

- 尽量先解码现有窗口
- 窗口不足时再 recv
- 每次产出 PCM 后立刻走输出节流
- 如果 stop 或 generation 变化，马上退出本轮

#### 分支 D：当前会话失败或结束

- 关闭 socket
- 重置解码器和接收窗口
- 如果外部已经 stop，就回到空闲
- 如果仍要求播放同一 URL，就延时后重试

这个循环已经足够覆盖你当前工程的真实需求。

## 8. HTTP 层应该怎样简化

当前版本在 HTTP 层做了很多“想得很周全”的事情，但对于现在这个项目，首要目标是稳定，不是全格式兼容。

### 8.1 只支持你当前真正需要的响应类型

第一版单文件闭环建议只明确支持：

- HTTP/1.1 200
- 非压缩 body
- 普通连续字节流 body

对于下面这些情况，不建议继续在主路径里深度兼容：

- gzip/deflate/br
- chunked
- 复杂的 Content-Type 推断策略
- 通过 HTML/JSON/RIFF/Ogg/FLAC 特征去做大规模分支判断

原因很简单：

- 你现在的主要场景是 DLNA 控制点给出一个 MP3 可播放 URL
- 当前目标是让播放闭环稳定下来
- 每多一种协议分支，调试成本都会陡增

第一阶段只要做到“遇到不支持的 HTTP 响应就尽快失败并打日志”，就比“边播边猜边修复”更可靠。

### 8.2 保留哪些 HTTP 工具逻辑

建议保留：

- parse_http_url
- resolve_ipv4_addr
- extract_http_header_value
- trim_ascii_whitespace

这些都属于刚需工具。

### 8.3 删除或弱化哪些 HTTP 分支

建议从主播放路径里删掉或降级成调试分支：

- parse_http_status_code_from_header 这种未形成完整策略的辅助函数
- 对 HTML、JSON、M3U、AAC、MP4、RIFF、Ogg、FLAC 的大范围签名分类
- payload preview 的高频日志

如果你确实需要排查异常流，建议把这些逻辑改成：

- 只在首包解码完全失败时打一条调试日志
- 默认关闭

不要让它们长期占据主循环。

## 9. MP3 解码层应该怎样简化

### 9.1 只保留两个关键目标

MP3 解码层在这个项目里只需要完成两个目标：

1. 从接收窗口里找出可解码帧
2. 把可解码帧稳定变成 PCM

其他行为都应该围绕这两个目标服务，而不是反过来主导流程。

### 9.2 推荐保留的最小策略

建议保留下面这组最小策略：

1. 滑动窗口
   - 使用 buf_start + bytes_in_buf 模型
   - 不要每消费一帧都 memmove
   - 仅在尾部空间不足或偏移过大时 compact

2. 首包 ID3 跳过
   - 只在流开头识别一次 ID3v2
   - 跳过后直接进入正常解码

3. 首次成功帧锁定采样率
   - 第一批成功帧里锁定 hz
   - 调一次 IIS 采样率映射
   - 不要在播放期间频繁抖动切频

4. 解码失败时优先“小步恢复”
   - 如果 samples == 0 且 frame_bytes == 0，优先单字节重同步
   - 如果窗口还不够大，先收更多数据
   - 不要在解码失败时过度使用大跨度跳过

### 9.3 不建议继续保留的复杂策略

下面这些逻辑不是永远不能做，而是不适合留在第一版单文件闭环里：

- 大量“非 MP3 内容签名”分类
- 复杂的双帧探测 probe_mp3_frame_from_buffer
- 大量 invalid_header_streak 特判
- 运行期高门槛的采样率切换防抖
- 太多 frame_bytes == in_buf 时的特殊推演

原因不是这些逻辑没有价值，而是它们会让你很难判断某次播放异常到底是：

- 网络没来数据
- 数据没对齐
- 真的不是 MP3
- 还是你自己的恢复逻辑把真实帧跳过去了

先把恢复策略收缩成“缺数据就收、无进展就小步重同步”，调试成本会低很多。

## 10. PCM 输出闭环应该放回播放器内部

这是当前项目里最值得立刻收口的一点。

### 10.1 现在的问题

目前 push_pcm_with_closed_loop 写在 wifi_task.cpp 里，但它实际处理的是：

- pending_frames 水位
- 队列高水位等待
- 队列低水位补偿
- PCM 写入 IIS

这明明是播放数据面逻辑，不是 WiFi 逻辑。

### 10.2 单文件方案的正确做法

既然你现在明确说“不拆文件”，那最直接的做法就是：

**把 push_pcm_with_closed_loop 直接并回播放器类的私有方法。**

也就是说，这个类自己负责：

- 看 IIS 当前 pending_frames
- 过高时等待 DMA 消耗
- 然后调用 iis::data_write
- 必要时调用 iis::fill_buffer_if_needed

这样才形成真正的闭环：

- 拉流在类里
- 解码在类里
- 输出节奏也在类里

而不是“上半截在播放器，下半截在 WiFi 任务”。

### 10.3 一个关键原则

播放器必须尊重 IIS 的现有 DMA 环形缓冲，不能再自己做第二层 PCM 缓冲队列。

原因很实际：

- iis 已经有 pending_frames
- iis 已经有预缓冲启动
- iis 已经有欠载填充

如果播放器再加一层自己的 PCM 队列，会出现：

- 你不知道当前延迟到底积在播放器里还是 IIS 里
- 水位阈值会变得不可推导
- 出现“快进感”时很难判断是谁在丢数据

所以单文件版本最重要的输出策略就是：

**只用 IIS 队列做唯一输出缓冲。**

## 11. 采样率切换策略应该收缩

当前代码里已经做了很多采样率兼容，这个方向本身没错，但规则可以更简单。

### 11.1 应保留的点

WS63 当前播放端确实要支持：

- 48000
- 44100
- 32000
- 24000
- 22050
- 16000
- 12000
- 11025
- 8000

这些映射不能丢。

### 11.2 应简化的点

第一版单文件方案建议这样处理：

- 首个稳定成功帧确定 current_hz
- 只在 current_hz 还没设置时调用 set_rate
- 运行过程中默认不主动切频

为什么这样更合理：

- 你的主要场景是一个 URL 对应一条稳定音频流
- 运行期频繁切频更像异常恢复策略，不是主路径需求
- 切频错误的代价很高，容易直接听成快进或变调

如果后续你确认有真实流会中途改采样率，再单独补“运行期切频策略”也不迟。

## 12. 会话中断和重连应该怎样设计

单文件版本不需要复杂的错误矩阵，只要做到下面这套规则即可：

### 12.1 这些事件都视为当前会话结束

- 用户 Stop
- URL 被新值覆盖
- socket connect/send/recv 失败
- HTTP 头不合法
- 服务器 EOF

### 12.2 会话结束后统一做三件事

1. close socket
2. reset 接收窗口和解码器状态
3. 清空 active_url 对应的临时运行状态

### 12.3 是否重连只看两件事

1. 现在还想不想播
2. 当前 generation 有没有过期

如果：

- play_requested 仍然为真
- requested_url 仍然有效
- generation 没被新请求覆盖

那就等待一个固定退避时间，比如 300 到 500ms，然后重连。

不要在单文件第一版里做：

- 区分十几种错误码做不同回退
- 首包失败和中途失败用完全不同的状态树
- 额外 probe 再决定要不要重连

这会把结构再次带回复杂化。

---

## 13. 建议删除的现有复杂逻辑

如果目标是“最基础闭环”，下面这些逻辑不建议继续留在主实现里：

1. classify_payload_prefix
2. log_payload_preview
3. probe_mp3_frame_from_buffer
4. parse_http_status_code_from_header
5. 大量 has_known_non_mp3_signature 分支
6. 复杂的 invalid_header_streak 恢复树
7. 运行中高门槛切采样率策略
8. 播放类对外暴露过多零散注册接口

这里要强调：

不是说这些逻辑永远不准出现，而是它们不应该占据第一版核心播放链。

第一版需要的是：

- 简单
- 可推理
- 出错时容易定位

而不是“看起来考虑了所有情况”。

---

## 14. 建议保留的现有逻辑

下面这些东西值得继续保留，只是要放在更正确的位置上，或者写得更收敛：

1. 使用 http_utils 解析 URL 和域名
2. 使用滑动窗口替代频繁 memmove
3. 首包和响应头使用较长超时，播放阶段使用较短超时
4. 单声道 PCM 扩展成双声道
5. 对 IIS 的 pending_frames 做高水位等待
6. 在欠载附近调用 fill_buffer_if_needed
7. SetURI 与 Play 解耦

这些都是当前工程真正有价值的经验，不应该在简化过程中一起丢掉。

---

## 15. 推荐的最终接口形态

如果你允许稍微收一下接口，我建议不要继续保留三组彼此独立的注册函数：

- iis_set_rate_set
- mp3_get_into_iis_set
- playback_queue_level_getter_set

单文件版本更适合的做法有两种。

### 方案 A：播放器直接依赖 IIS

这是我更推荐的方案。

原因：

- 当前项目里播放器就是给 IIS 喂 PCM
- 没有第二个下游输出目标
- 直接依赖更简单，链路更短

这样播放器类内部直接调用：

- iis::set_rate_of_iis
- iis::data_write
- iis::fill_buffer_if_needed
- iis::pending_frames

就够了。

### 方案 B：保留一个统一的 OutputHooks

如果你想暂时保留“播放器不直接 include iis”的形式，也不要继续拆成三组 setter。建议改成一个统一输出绑定结构：

- set_rate
- write_pcm
- get_queue_level
- fill_if_needed

这样至少边界是清晰的：播放器只有一个输出端口，而不是三四个散口子。

## 16. 推荐的实现顺序

虽然这份文档不要求你现在就写代码，但真正落地时，建议按下面顺序做，不要一口气全改：

1. 先明确类身份
   - 把它视为播放服务，不再视为“解码器类”

2. 先收口状态
   - 把 URL、播放请求、活动会话、current_hz 收进类内

3. 再把 push_pcm_with_closed_loop 并回类内
   - 让输出节奏闭环回到播放器

4. 再删减复杂探测分支
   - 先保留最少的 ID3 跳过和小步重同步

5. 最后再决定是否保留更复杂的兼容逻辑
   - 比如 ICY、额外格式探测、运行时切频

这样改的好处是，每一步都能单独验证，不会出现“是结构改坏了还是某个细节改坏了”这种混淆。

---

## 17. 一句话方案总结

如果只允许保留一个文件，那么当前工程里最合理的 minimp3 不是“继续叠加特判的万能播放器”，而应该是：

**一个长期运行的播放服务类，自己持有播放会话状态，自己完成 HTTP 拉流和 miniMP3 解码，自己根据 IIS 水位做 PCM 输出节流，并且只依赖 IIS 现有的 DMA 队列作为唯一下游缓冲。**

这就是最适合当前项目布局的“最基础闭环”。

它不花哨，但最容易做对，也最容易调稳。
